# Theme previews, reusable identity and selected references

Read when extending a selected theme across platforms, creating reusable branding
or handing off a concept choice. Use the parts relevant to the request; a small
component change does not require a concept gallery, brand kit or backup archive.

## Separate the decisions

Record the selected reference and approval scope in the existing project handoff:

- Theme/feel: palette, typography, material and identity cues.
- Layout: proportions, hierarchy, placement and responsive composition.
- Flow: screens, actions and meaningful states.
- Assets: approved logo/artwork sources and export variants.

For example, “I like C's fonts and colors; show me the phone app” selects the
theme. It does not request another theme vote or approve every desktop/mobile
layout. Extend that identity to a bounded mobile study. Conversely, an approved
exact screen should be faithfully implemented unless a practical issue requires
a clearly explained adaptation.

When the user requests a preview before implementation, finish the preview and
hand it over without claiming the full product is built. If implementation is
already authorized and no design choice remains, continue into a complete slice.

## Show enough to make the choice concrete

Use a small coherent set of representative screens or states, not an exhaustive
product redesign by default. A resource list, detail, primary action and result
may show more than four unrelated home screens. Preserve the selected palette,
font roles and mark while adapting to platform density and navigation conventions.
System-controlled surfaces may only partially reflect the application's theme.

Provide screenshots the user can see, plus editable/live previews when useful.
Include direct routes or a single-screen mode for phone inspection. Check for
overflow, clipped labels, safe-area problems, misleading status and broken assets.
Useful preview controls should work; remaining concept actions should explain
their limitation rather than pretending to contact a backend. Call a browser mock
of a native app an HTML study, and distinguish browser screenshots from real-device
verification.

## Separate identity assets when requested

Keep brand source masters in a stable, project-appropriate asset directory rather
than buried in a demo screen. An identity kit can include the mark, wordmark,
lockups, light/dark or monochrome variants, shared tokens and relevant exports.
Do not generate all imaginable formats before there is a need.

Use editable vector geometry for simple logo refinement and standard icons.
Use generated raster artwork for suitable illustration or product-context needs,
with source prompts and provenance recorded. Keep full source assets separate
from compressed runtime derivatives and from concept screenshots.

For fonts, retain source and license notices when bundling. Self-host selected
fonts where appropriate for predictable previews and runtime delivery; verify
the intended face actually loaded. Outlined wordmarks avoid a font dependency in
exported logos, while interface text should remain native text.

For app icons and favicons, check the actual target's requirements before export:
size, transparency, safe region, adaptive layers and appearance variants differ.
Inspect the mark at small sizes, under relevant masks and on light/dark surfaces.
File dimensions or valid XML alone do not prove native integration, store approval
or launcher/device behavior. Label what was and was not verified.

## Leave one current reference set

After selection, make the current website/app/brand references easy to find. A
small review hub is useful for multi-surface work; links in the handoff suffice
for a smaller task. Do not leave a “choose a direction” prompt as the current
entry point after the user has chosen. Keep design state and implementation state
separate: selected, exploratory, implemented and visually verified.

When asked to remove old designs, inspect callers/shared assets first. Clean
obsolete pages, comparison exports, styles, tests and selection notes together;
retain the chosen references, useful source art, licenses and engineering plans.
Do not rewrite shared styles used by another active product without checking.
Do not infer authority to erase unrelated work or modify cloud resources.

Use existing version history or a proportionate recoverable archive when cleanup
needs recovery. If moving files outside the project, validate resolved source and
destination paths and preserve a locator. Check critical selected files after the
move; verify archive integrity if claiming a verified backup. Avoid repeated full
snapshots and archiving secrets. Update verification to target the current design
rather than leaving a test runner that requests deleted variants.

Before handoff, distinguish these claims explicitly: saved on disk, committed,
backed up, pushed and deployed. A local archive is not a remote backup. Do not
commit, publish or deploy merely to make “saved” sound stronger.
